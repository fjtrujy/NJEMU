# PS2 controller interrupts, PADMAN cadence, and IOP event buffering

Date: 2026-10-10
Scope: PS2/CPS1 issue #15, especially missing short Square presses and
partial simultaneous-button chords. **Investigation only; no input behavior
changes are proposed as a default.**

Issue: https://github.com/fjtrujy/NJEMU/issues/15#issuecomment-6098377002

## Executive finding

The DualShock 2 communicates over a host-clocked serial controller bus.
The console initiates a read command (`0x01, 0x42`) to obtain button bits.
The controller does **not** asynchronously interrupt the console on every
button press. SIO2 completion interrupts are generated by *transactions*,
not by the physical switch independently.

PS2SDK's PADMAN already runs on the IOP, independent of the EE application.
It registers IOP VBlank handlers; `VblankStart()` signals
`EF_VB_TRANSFER`, `TransferThread()` calls `pdTransfer()`, the per-port
`UpdatePadThread()` reads/validates the response, and `DmaSendEE()`
publishes the most recent packet in double-buffered EE memory. The stock
PS2SDK implementation is therefore **VBlank-driven** (typically ~60 Hz for
NTSC, ~50 Hz for PAL), not 250 Hz simply because EE calls `padRead()`
every 4 ms. Individual timing is subject to controller/device and IOP
scheduling, so the actual *fresh-packet* cadence should be measured.

This is specifically relevant to NJEMU: its `ps2_joystick_driver` in
`/Users/fjtrujy/Projects/ps2_drivers/src/ps2_joystick_driver.c` loads
the bundled `padman` IRX and initializes `libpad`. NJEMU's
`src/ps2/ps2_input.c` uses that `padRead()` API.

### Important distinction

- An **IOP edge queue** retains presses/releases that *PADMAN has observed*
  but the EE has not yet consumed. It solves dropped history across the
  IOP-to-EE handoff or emulation delays.
- A **higher physical polling frequency on the IOP** is needed to observe
  a press/release that falls entirely between two ordinary PADMAN reads.
  An IOP queue running at the same ~60 Hz cannot reconstruct unseen input.
- An **EE input worker** does not increase the physical controller polling
  rate. Previous PCSX2 tests with a 4 ms EE worker showed no improvement.

## What is and is not interrupt-driven

The IOP has an SIO2 IRQ, but the SIO2 bus is clocked by the host and the
interrupt signals transfer progress/completion. It is not a per-button
hardware IRQ from the DualShock 2. Similarly, PADMAN's VBlank handler
signals its *existing polling thread* to start transfer work. Processing
input in an interrupt handler would also not safely execute an emulated
CPS1 game action immediately: the 68000 must observe a consistent input
register state during its scheduled execution.

No public per-button change callback or input-event FIFO is offered by
the `libpad` API used by NJEMU. Its `padRead()` copies the latest
DMA packet; `padGetFrameCount()` is explicitly listed as unimplemented
in the current PS2SDK source. The IOP packet/EE DMA structures do contain
frame sequence numbers and double buffering; they are *snapshots*, not an
unbounded press/release history.

## How other input systems address lost presses

Most systems divide the problem into two layers:

1. **Acquisition and transport:** collect hardware/OS events as they arrive,
   store ordered press/release transitions with sequence numbers and
   timestamps, and drain them during the game's next update. SDL has an
   event queue consumed by `SDL_PollEvent`; Unity explicitly buffers
   device events between game updates.
2. **Game-action buffering:** some games queue actions pressed shortly
   before they become legal (e.g., jump before landing, attacks during
   recovery). This is a **gameplay decision** with an expiration window,
   not proof that physical sampling was lost.

For an emulator, layer 1 is appropriate to investigate. Applying layer 2
globally can change the original CPS1 game's recovery/cancel semantics,
which is not acceptable as a transparent emulator correctness fix.
Similarly, extending a 3 ms tap into an entire emulated-frame button hold
is a fidelity tradeoff, not a guaranteed lossless translation.

## Viable approaches

| Approach | Can recover PADMAN-observed transitions between EE frames? | Can recover transitions that PADMAN never observed? | Risk |
| --- | --- | --- | --- |
| Current per-emulated-frame EE `padRead` | No | No | Baseline |
| More frequent EE reads / an EE thread | Sometimes, only while distinct DMA updates are published | No | Scheduling overhead |
| **IOP event ring, stock PADMAN poll cadence** | **Yes** | **No** | Custom IOP integration, DMA and queue lifecycle |
| Higher-frequency IOP SIO2 polling, with event ring | Yes | Potentially (if actual fresh transactions increase) | High: PADMAN/SIO2 timing, rumble, multitap, other device traffic |
| Stretch/latch every observed press for a frame | Can make short observed taps visible | No | May change CPS1 gameplay/input semantics |

A dedicated producer queue with a capacity such as 32 or 64 events is
reasonable for an **opt-in prototype**. Each event would contain:
`sequence`, IOP frame/timestamp, port, slot, pressed bitmask, released
bitmask; the latest held state would be stored separately. A dropped-event
counter is mandatory. The EE should acknowledge the last fully consumed
sequence: **do not clear the ring immediately on DMA initiation** or while
the consumer might still need those entries. Use a bounded, versioned
buffer format with well-defined overflow and reconnect handling, and
preserve simultaneous button masks.

Do not add an independent SIO2-polling IOP thread on top of PADMAN without
coordinating with PADMAN's ownership of SIO2. Such a second driver can race
with controller configuration, multitaps, rumble, and other IOP traffic.
A faster-driver experiment should modify or replace the polling schedule
in a test-only PADMAN build after the baseline is characterized.

## Recommended sequence, with objective gates

### Stage 1: Measure actual fresh packet delivery (no gameplay change)

Instrument the stock IOP/EE path to record per-controller frame sequence,
valid reads, duplicates and skipped publications. PADMAN already increments
an internal per-port frame and embeds it in its EE DMA buffers. The
`PS2_INPUT_PROFILE=ON` build now reads this counter **diagnostically**
from the existing double-buffered new-PADMAN DMA area, after libpad's
`padRead()` performs the necessary cache synchronization. This avoids
patching libpad or changing the IOP's published API.

The decoder is specifically for PS2SDK's newer 128-byte PADMAN records
(frame at byte offset 88, record offsets 0 and 128), verified by
synthetic wrapped/duplicate/skipped-sequence tests. Older 64-byte ROM
PADMAN records have a different layout and are **not** supported by
this diagnostic.

`[ps2_padman]` prints `reads`, `advanced`, `repeated`, `skipped`,
`backward`, and the last frame after every 600 CPS1 input samples.
With `PS2_INPUT_THREADED=ON` and `PS2_INPUT_PROFILE=ON`,
`[ps2_padman_worker]` reports those metrics from the 4 ms EE worker
over 600 CPS1 frames. These count IOP-to-EE **publications**, not
physical SIO2 transactions.

#### Measured PCSX2 cadence (CPS1 dino, NO_GUI, 240p)

| Steady-state metric over 600 emulation frames | Normal PS2 driver | 4 ms EE worker |
| --- | ---: | ---: |
| Valid reads | 600 | 2,479 |
| Distinct new DMA frames | 598 | 598 |
| Repeated DMA frames | 2 | 1,881 |
| Skipped frame sequence values | 0 | 0 |
| Backward frame sequences | 0 | 0 |

Additional steady worker windows observed 599, 598, 598 and 599 new
publications over approximately ten seconds each. Normal PS2 sampling
reported 598, 597 and 599, with one skipped value in the 597 window.
The **initial startup window** must be excluded: asynchronous
initialization/boot scheduling yielded 779 frame advances and 16 skips.

The observed steady PCSX2 publication rate is about **59.8-59.9 Hz**.
Reading the buffer 250 times a second does not produce 250 distinct
controller publications, explaining why the 4 ms EE-thread experiment
did not improve short-tap detection.

The corresponding ignored local logs are:
`build_issue15_pcsx2_dino/pcsx2_padman_cadence.log` and
`build_issue15_async_cps1/pcsx2_padman_cadence_thread.log`.
The physical PS2 did not respond at its previous network address
during this investigation. PCSX2 results alone cannot establish the
real DualShock polling period or physical button acquisition rate.

To repeat: use `-DPS2_INPUT_PROFILE=ON` on a CPS1 PS2 build, and
optionally `-DPS2_INPUT_THREADED=ON` on a second comparable build.
Allow the DualShock mode handshake to finish, then capture at least
three steady 600-frame windows with the same game/configuration.
Do not mix startup and steady windows.

Remaining questions: Does a physical PS2 show the same publication
cadence? Are individual face-button edges absent from actual IOP
acquisition? How do PAL and NTSC output modes affect polling?

### Stage 2: Prototype IOP edge recording at the existing cadence

Attach a bounded ring to the point **after a valid controller response**
in PADMAN's `UpdatePadThread`, not to the EE `padRead()` consumer.
Preserve `pressed = current & ~previous` and
`released = previous & ~current` (with the correct active-low conversion).
Expose the ring via a versioned, optional IOP-to-EE mechanism, without
changing the existing libpad ABI. The EE drains it before CPS1 input-port
update. Track `produced/consumed/dropped` and measure delay and RAM usage.

If losses in the stock setup are only between IOP acquisition and EE
consumption, the IOP queue can help while retaining stock polling rate.
If losses already occur in physical acquisition, Stage 2 alone cannot
improve the very short taps.

### Stage 3: Only if necessary, evaluate higher-rate IOP acquisition

Test a **separate** PADMAN/SIO2 experimental build with a controlled
poll interval (e.g. 4 ms), using exclusive SIO2 ownership and complete
teardown. Measure genuinely new packets, CPU/IOP load, audio stability,
controller types, multitaps, rumble, and reconnection. Do not enable this
by default or assume PCSX2 models physical bus timing exactly.

If Stage 3 yields more genuine physical samples, feed those events to
the Stage 2 ring and compare against Stage 1. Otherwise, remove the
complexity. The safer production path remains normal PADMAN with the
existing PS2 input corrections.

### Stage 4: Verify CPS1 consumption and original game behavior

Trace the **active-low port-1 Attack bit `0x0010`**, including simultaneous
D-pad + face buttons, alongside IOP events and emulated-frame numbers.
Distinguish:
(a) button transition never acquired;
(b) acquired on IOP but lost en route to EE;
(c) delivered by EE but not represented on the emulated port;
(d) represented in the port but legitimately rejected by game's attack
recovery state.

A physical PS2 + DualShock test is essential before selecting the final
approach. A synthetic PCSX2 keyboard test cannot distinguish controller
hardware acquisition effects from PCSX2 host-event timing.
