# PSP XMB metadata and artwork

PSP packages keep two version identities: `VERSION_STR` is the human-facing
release version (for example, `3.0.0`), while `NJEMU_RUNTIME_BUILD_ID` retains
the Git-derived detailed build identity (for example, `3.0.0 (abcdef12)`).
Other platforms continue to use the detailed version in their UI. The shared
`cmake/NJEMUVersion.cmake` derivation is the single source of version truth.

The PSP SDK's `create_pbp_file()` builds the EBOOT using these inputs:

| PBP entry | Source | Purpose |
| --- | --- | --- |
| `PARAM.SFO` | Generated by `mksfoex` | `NJEMU <core> <release>` title, numeric `APP_VER` (`major.minor`), `MEMSIZE=1` |
| `ICON0.PNG` | `data/<core>.png` | Existing 144x82 XMB icon |
| `PIC0.PNG` | Empty | Optional supplementary overlay, not needed |
| `PIC1.PNG` | `data/psp/<core>_pic1.png` | 480x272 PSP XMB background |
| `DATA.PSP` | Built executable | Emulator executable |

The four original backgrounds are kept as independent PNG assets rather than C
arrays and do not occupy emulator runtime texture storage. Regenerate them on
macOS with `swift tools/generate_psp_backgrounds.swift data/psp` when updating
the NJEMU brand. The generated PNGs are checked into the repository so CI does
not require Swift or a graphics library.

To inspect an EBOOT, run `unpack-pbp EBOOT.PBP` in an empty directory, compare
`ICON0.PNG` and `PIC1.PNG` against the corresponding files in `data/`, and
inspect `PARAM.SFO` using `strings` or an SFO parser. The PSP CI workflow
checks these assets after installation. `APP_VER` is deliberately the SDK's
numeric major/minor representation (for example `3.0`) rather than the full
Git build identity. `DISC_VERSION` and `PSP_SYSTEM_VER` may remain at the SDK's
default `1.00`; neither is NJEMU's application version. The full SHA identity
remains available in emulator diagnostics.
